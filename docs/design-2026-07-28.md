# MCP 2026-07-28 design

This module targets MCP `2026-07-28`.

## Goals

- Make every request self-contained and validate its protocol version and
  client capabilities at the dispatch boundary.
- Keep the common server API small, typed, async-first, and transport-neutral.
- Generate protocol bookkeeping (`_meta`, `resultType`, cache metadata,
  discovery, and transport headers) in the SDK rather than in application
  handlers.
- Support ordinary handlers and multi round-trip request (MRTR) handlers
  without exposing server-to-client JSON-RPC requests.
- Keep extensions possible through explicit capability and raw JSON escape
  hatches without weakening validation of core methods.
- Make a shared `Server` safe to use behind stateless HTTP requests.

## Protocol surface

Requests are stateless and carry protocol version, client capabilities, and
optional client identity in `params._meta`. The server does not retain
negotiated client state. HTTP uses one POST per JSON-RPC message and has no MCP
session identifier or GET event stream. `subscriptions/listen` provides
long-lived notifications, while MRTR carries elicitation, sampling, or roots
input requests inside an `input_required` result.

Tasks are represented through negotiated extensions. Deprecated roots and
sampling capability shapes are isolated in `DeprecatedClientCapabilities` for
MRTR interoperability and are not advertised by default.

## Package layout

The package graph has an explicit dependency direction. JSON-RPC framing is
not reimplemented by a transport adapter, and a transport does not inspect an
MCP method name. The root package remains the ergonomic facade, while the
lower-level packages are usable by custom transports.

- `shiguri-01/mcp/jsonrpc`: JSON-RPC 2.0 envelope types (`RequestId`, request,
  notification, response, and error object), single-message codec, and
  constructor-level envelope invariants. It has no MCP or I/O dependency;
- `shiguri-01/mcp/transport`: opaque frame exchange (`OutboundFrame`,
  `InboundFrame`, `FrameTransport`, and `FrameStream`) and transport errors.
  Frames contain a body and transport headers, never a parsed JSON-RPC value;
- `shiguri-01/mcp`: MCP wire model, method-specific params/results, request
  builder, stateless server registry/dispatcher, MRTR, cache policy,
  notification builders, and MCP errors;
- `shiguri-01/mcp/schema`: JSON Schema 2020-12 builders and MCP-specific
  validation helpers;
- `shiguri-01/mcp/auth`: native MCP Authorization discovery, registration,
  PKCE, token, scope, issuer, and resource-binding primitives;
- `shiguri-01/mcp/stdio`: native newline framing and multiplexing;
- `shiguri-01/mcp/http`: native Streamable HTTP frame adapter, streaming, header
  validation, Origin policy, subscriptions, and optional MCP Authorization
  orchestration through an explicit host provider.

The root package depends only on `jsonrpc` and `transport`; it does not depend
on HTTP, stdio, or native-only APIs. A custom WebSocket, QUIC, embedded, or
test transport implements `FrameTransport` without importing HTTP/stdio and
without learning JSON-RPC field layout. Native adapters keep their streaming
and cancellation requirements at the adapter boundary; they must use the
same root codec rather than defining another envelope type.

## Request and result model

`Client` owns only defaults: implementation identity, preferred protocol
version, and capabilities. Every request copies these values into a typed
`RequestMeta`; there is no negotiated connection state. `RequestOptions` adds
progress, log level, MRTR responses/state, and vendor metadata for one request.

The server parses the required request metadata before routing and gives every
handler a `RequestContext`. The context contains only request-scoped protocol
data. Transport/authentication data can be added by the transport boundary,
but must not be stored as a global current client.

Application handlers return `HandlerOutcome[T]`:

- `Complete(T)` for an ordinary successful result;
- `InputRequired(InputRequiredResult)` for MRTR from `tools/call`,
  `resources/read`, or `prompts/get`.

The dispatcher rejects `InputRequired` for other methods. It stamps every
complete result with `resultType: "complete"` and server identity in `_meta`.
Input-required results must contain at least one input request or opaque request
state. A retry carries input responses and state on a new JSON-RPC request ID.

Protocol errors, application-level tool errors (`isError`), and local
transport/decode errors remain distinct.

## Server API

The primary registration API is `Server::tool`: it is typed, async-first,
receives a `RequestContext`, and returns `HandlerOutcome`. `Server::tool_raw`
is the explicitly named escape hatch for extensions or applications whose
input type is intentionally dynamic. Handlers that do not need context can
ignore the context parameter.

Server capabilities are derived from registered tools, resources, prompts,
completions, and configured subscription support. `server/discover` is always
registered. Lists preserve registration order for deterministic output.

`CachePolicy` is configured by result family. It contains non-negative `ttlMs`
and a `public`/`private` scope. Discovery and the five list/read result families
always contain both cache fields.

## Client API

The transport-neutral client creates correct JSON-RPC messages and decodes
typed outcomes. `Client::exchange` accepts any `FrameTransport`; its input and
output are protocol values while the adapter owns framing and connection
lifetime. High-level HTTP and stdio clients provide `discover`, list/call/read
verbs, pagination helpers, and bounded MRTR resolution. Raw request/response
methods remain available as explicitly named `request_raw`/`*_raw` escape
hatches for extensions. Unknown `resultType` values are never
silently treated as complete for the modern protocol.

The canonical JSON conversion contract is MoonBit's `@json.ToJson` and
`@json.FromJson`. `FromJson::from_json` is the structural decoder and reports
`@json.JsonDecodeError`; it is not a second public parsing vocabulary. Values
that have protocol invariants are constructed through their named constructor
or typed decode operation, so an invalid value cannot enter a registered
handler. The only string boundary is `@json.parse`.

MRTR drivers require a maximum number of rounds, preserve request state
verbatim, collect responses by server-assigned key, and allocate a fresh
request ID for every retry.

## Subscriptions and notifications

`subscriptions/listen` is represented as a long-lived stream, not an ordinary
completed request. A subscription declares its notification filters. The first
event is an acknowledgement, and every stream event carries the listen request
ID as `io.modelcontextprotocol/subscriptionId`.

Request-scoped progress/log messages remain on the request response stream.
Subscription events never carry request-scoped messages. Cancellation is an
SSE close on HTTP and `notifications/cancelled` on stdio.

## HTTP boundary

There is one POST endpoint and no protocol session. Each request validates:

- Origin policy;
- `Content-Type` and both required Accept media types;
- `MCP-Protocol-Version` against request `_meta`;
- `Mcp-Method` against the JSON-RPC method;
- required `Mcp-Name` against tool/resource/prompt names;
- MCP parameter headers declared with `x-mcp-header`.

Header/body mismatch is JSON-RPC `-32020` with HTTP 400. Unsupported protocol
version is `-32022`; missing required client capability is `-32021`.

Optional HTTP authorization uses a host-supplied provider for HTTP delivery,
user-agent interaction, cryptographic entropy, and destination policy. The SDK
performs protected-resource and authorization-server discovery, PKCE S256,
client registration selection, issuer validation, scope step-up, refresh-token
fallback, and issuer/resource-bound credential storage. The built-in policy
requires HTTPS and rejects reserved literal addresses. Insecure loopback
endpoints require an explicit opt-in. Concrete providers must additionally
validate resolved addresses and every redirect hop before sending data.

## Validation strategy

Protocol black-box tests exercise public request/response behavior. Focused
white-box tests cover codec boundaries, JSON Schema applicators, transport
header validation, stream state machines, and failure paths. Native integration
executables verify UTF-8 and incremental delivery through a real stdio process
and HTTP socket. Portable packages are tested on native, JS, and wasm-gc.

The final gate is:

1. `moon check --target all`;
2. `moon test --target native`, `moon test --target js`, and
   `moon test --target wasm-gc`;
3. native stdio process and HTTP socket roundtrips;
4. `moon info && moon fmt`, followed by a clean generated-interface diff;
5. the frozen MCP 2026-07-28 server and client conformance requirements;
6. an independent implementation, security, and specification review.
