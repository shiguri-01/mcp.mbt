# MCP 2026-07-28 redesign

This module intentionally targets only MCP `2026-07-28`. It does not provide
an adapter for the connection-oriented protocol eras.

## Goals

- Make every request self-contained and validate its protocol version and
  client capabilities at the dispatch boundary.
- Keep the common server API small, typed, async-first, and transport-neutral.
- Generate protocol bookkeeping (`_meta`, `resultType`, cache metadata,
  discovery, and transport headers) in the SDK rather than in application
  handlers.
- Support ordinary handlers and multi round-trip request (MRTR) handlers
  without exposing server-to-client JSON-RPC requests.
- Keep extensions possible through explicit capability and raw JSON escape
  hatches without weakening validation of core methods.
- Make a shared `Server` safe to use behind stateless HTTP requests.

## Deliberate breaking changes

The following APIs and wire behavior are removed:

- `initialize`, `notifications/initialized`, lifecycle/session state, and
  negotiated state stored on `Server`;
- `ping`, `logging/setLevel`, and connection-wide log level;
- `resources/subscribe`, `resources/unsubscribe`, and local subscription state;
- core task capabilities (tasks are an extension);
- `Mcp-Session-Id`, the HTTP session store, DELETE session termination, GET
  SSE, and SSE resumption;
- client methods whose only purpose was to build the removed messages.

Deprecated roots, sampling, and logging wire shapes are not exposed by the
high-level API. Extensions can still represent them explicitly when required.

## Package layout

The public wire model, request builder, server registry, and dispatcher stay in
`shiguri-01/mcp`. MoonBit packages are import boundaries rather than file
names, so the root package is split into small cohesive source files instead of
forcing users to coordinate `protocol`, `client`, and `server` imports.

- `shiguri-01/mcp`: protocol model, codecs, client request builder, stateless
  server, MRTR, cache policy, notification builders, and errors;
- `shiguri-01/mcp/schema`: JSON Schema 2020-12 builders and MCP-specific
  validation helpers;
- `shiguri-01/mcp/stdio`: native newline framing and multiplexing;
- `shiguri-01/mcp/http`: native Streamable HTTP exchange, streaming, header
  validation, Origin policy, and subscriptions. OAuth authorization is left to
  an upstream middleware or a dedicated future adapter rather than exposed as
  an incomplete boolean hook.

Transport packages depend on the root package. The root package never depends
on a transport or native-only API.

## Request and result model

`Client` owns only defaults: implementation identity, preferred protocol
version, and capabilities. Every request copies these values into a typed
`RequestMeta`; there is no negotiated connection state. `RequestOptions` adds
progress, log level, MRTR responses/state, and vendor metadata for one request.

The server parses the required request metadata before routing and gives every
handler a `RequestContext`. The context contains only request-scoped protocol
data. Transport/authentication data can be added by the transport boundary,
but must not be stored as a global current client.

Application handlers return `HandlerOutcome[T]`:

- `Complete(T)` for an ordinary successful result;
- `InputRequired(InputRequiredResult)` for MRTR from `tools/call`,
  `resources/read`, or `prompts/get`.

The dispatcher rejects `InputRequired` for other methods. It stamps every
complete result with `resultType: "complete"` and server identity in `_meta`.
Input-required results must contain at least one input request or opaque request
state. A retry carries input responses and state on a new JSON-RPC request ID.

Protocol errors, application-level tool errors (`isError`), and local
transport/decode errors remain distinct.

## Server API

The primary registration APIs are typed and async-first. They receive a
`RequestContext` and decoded input. Convenience `simple_*` registrations accept
handlers that need neither context nor MRTR. A raw method registration is the
escape hatch for negotiated extensions.

Server capabilities are derived from registered tools, resources, prompts,
completions, and configured subscription support. `server/discover` is always
registered. Lists preserve registration order for deterministic output.

`CachePolicy` is configured by result family. It contains non-negative `ttlMs`
and a `public`/`private` scope. Discovery and the five list/read result families
always contain both cache fields.

## Client API

The transport-neutral client creates correct JSON-RPC messages and decodes
typed outcomes. High-level transport clients provide `discover`, list/call/read
verbs, pagination helpers, and bounded MRTR resolution. Raw request/response
methods remain available for extensions. Unknown `resultType` values are never
silently treated as complete for the modern protocol.

MRTR drivers require a maximum number of rounds, preserve request state
verbatim, collect responses by server-assigned key, and allocate a fresh
request ID for every retry.

## Subscriptions and notifications

`subscriptions/listen` is represented as a long-lived stream, not an ordinary
completed request. A subscription declares its notification filters. The first
event is an acknowledgement, and every stream event carries the listen request
ID as `io.modelcontextprotocol/subscriptionId`.

Request-scoped progress/log messages remain on the request response stream.
Subscription events never carry request-scoped messages. Cancellation is an
SSE close on HTTP and `notifications/cancelled` on stdio.

## HTTP boundary

There is one POST endpoint and no protocol session. Each request validates:

- Origin policy;
- `Content-Type` and both required Accept media types;
- `MCP-Protocol-Version` against request `_meta`;
- `Mcp-Method` against the JSON-RPC method;
- required `Mcp-Name` against tool/resource/prompt names;
- MCP parameter headers declared with `x-mcp-header`.

Header/body mismatch is JSON-RPC `-32020` with HTTP 400. Unsupported protocol
version is `-32022`; missing required client capability is `-32021`.

## Validation strategy

Black-box tests use official schema examples and hand-written negative vectors.
They cover required metadata, discovery, result stamping, version/capability
errors, deterministic cacheable lists, MRTR restrictions and retry state,
resource-not-found behavior, stdio framing, stateless HTTP headers, Origin
rejection, and subscription ordering/correlation. Native integration tests cover
stdio and HTTP; the transport-neutral package is checked on all stable targets.

The final gate is:

1. `moon check --target all --warn-list +73`;
2. `moon test --target native` and transport-neutral JS/wasm-gc tests;
3. `moon info && moon fmt`;
4. public `.mbti` and full diff review;
5. an independent implementation and specification review.
